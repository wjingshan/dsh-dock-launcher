# 事后总结：dsh web GUI 无响应（会话恢复忙循环）

日期：2026-09-13
状态：已恢复（重启 + 换用 v3 会话格式后缓解）

## 现象

在 dsh Web GUI 里发消息没有任何反应，但服务本身「活着」：

- `127.0.0.1:3080` 端口正常监听，HTTP 请求 0.03s 即有响应（返回 401 是正常认证拦截）；
- Edge 浏览器仍保持 12 条 WebSocket 连接。

结论：不是服务挂了，而是**主进程的事件循环被拖死**——处理 WebSocket 消息的活儿排不上队。

## 根因

对主进程采样调用栈，几乎 100% 的时间都耗在「海量文件 stat 回调 → Promise / 微任务风暴」这条链路上，事件循环被刷满。

触发源（两个叠加）：

1. **恢复/重放一个 17MB 的巨大会话**（`session-be2de5d2`，37016 帧）；
2. **扫描大项目目录**（`/Volumes/Work-2T-Mac/…`，780MB / 1325 文件，外部卷）。

现场数据：

- 16:50 启动后 2 分钟烧掉 1 分 15 秒 CPU；
- 内存 765MB（峰值 1.1GB）；
- 会话文件 `session.jsonl.zstd` 17MB + 5.1MB，`session.lock` 被它持有。

## 归因澄清（重要）

最初怀疑是「回滚前的 0.22.0 版本导致」，**经核实不成立**：

- 0.22.0 只改了开关 App 的**启动/停止 dsh 的方式**（走 `dsh-doctor launch` / 发 SIGINT），以及开启 doctor 的 `autoRepair`；它**不改变 dsh 内部的会话恢复与文件扫描逻辑**。
- 忙循环的直接根因是 **dsh 自身恢复 17MB 大会话 + 扫描目录**，与开关 App 版本无关。
- 0.22.0 开启的 doctor 监控（5s heartbeat + 健康探测）确实在 dsh 主进程内额外运行，事件循环已满时是**次要加重因素**，但量级远小于会话重放的 stat 风暴。

「回滚后好转」的真实原因是：17:33 重启时 dsh **换用了 v3 会话格式**（新文件 `session.v3.jsonl.zstd`，5MB），旧的 17MB `session.jsonl.zstd`（16:41 停止增长）不再被重放——是**重启 + 新格式**缓解了问题，而非「回退版本」本身。

## 根因链条

```
单会话无限增长（本对话累积到 17MB / 37016 帧）
  → dsh 重启时恢复/重放该会话（逐帧解压）
  → 叠加启动时的项目目录扫描
  → 海量文件 stat 回调 → Promise/微任务风暴
  → 事件循环被刷满，WebSocket 消息无法被及时处理
  → GUI 表现为「无响应」，但端口/HTTP 仍正常
```

## 避免措施（检查清单）

### 会话层（主因）
- [ ] **控制单会话大小**：17MB 是异常值（正常会话通常 < 1–2MB）。超长对话应主动开新会话，或确认 dsh 的 compaction 是否对超长会话生效。
- [ ] **定期清理旧的巨大会话**：`~/.dsh/sessions/` 下按月归档/删除不再需要的 `session-*.jsonl.zstd`。
- [ ] 观察会话是否应切到 v3 格式（17:33 重启后 `session.v3.jsonl.zstd` 出现，旧文件停止增长）。

### 目录层（加重因素）
- [ ] 避免让 dsh 的工作区指向**外部卷的巨型目录**（`/Volumes/…`）；必要时用更小的项目根或 `.gitignore`/排除规则收窄扫描范围。

### 监控层（早发现）
- [ ] 健康探测**不能只看 TCP 端口**——本例端口一直通。应加「事件循环是否响应」的探测（例如 WebSocket ping 往返，或一个轻量 `/api/health` 带超时）。
- [ ] 对 dsh 主进程监控 CPU 曲线：启动后前 2 分钟若 CPU 持续打满，即为恢复/扫描忙循环的早期信号。

### 开关 App 侧（吸取的教训）
- [ ] 若日后重引入 doctor 监控 / launcher，需评估其在 dsh 主进程内的额外开销；dsh 假死（进程活着但事件循环卡住）时，launcher 的重启机制要能识别「忙循环假死」，而不只是「进程退出」。
- [ ] 版本回滚前先定位**真正的根因**：本次「回滚有效」是重启 + 会话格式切换的副产物，而非版本差异，避免把修复归因到错误的改动上。
